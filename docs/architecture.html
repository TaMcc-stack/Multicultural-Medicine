系统架构与数据流转

面向普通群众的民族健康科普问答系统：从用户口语化提问，到可溯源的结构化回答。 本文档说明三大进程的职责划分、技术选型依据、对外接口清单， 一条提问在系统内部的完整流转路径，以及前端为了让这条流程不出错所做的几处设计。

系统里有两个闭环：一个是「提问 → 检索 → 可溯源回答」，另一个是 「发现知识库缺什么 → 用户确认这个需求 → 补录文献 → 审核入库 → 下次能答上」。 前者对用户，后者对运营；04 节的两条链路分别走这两个环。

04数据流转

A · 问答主链路

以「白族糖尿病患病率是多少？」为例，一次提问在系统内的完整路径：

  1. 前端发起理解 POST /api/understand
    前端把当前问题连同最近几轮上下文一起发出。后端依次跑三层：
    • 规则层 —— 民族 / 疾病 / 意图关键词、泛民族词、医疗安全正则
    • 大模型层 —— 补全槽位、常识推理、判定是否索要用药建议
    • 历史继承 —— 追问省略疾病名时，从上一轮继承
    返回 {民族, 疾病, 意图, 指标, 泛化标记, 用药标记, 状态}
  2. 前端按状态决定是否放行
    缺民族且非泛化 / 非用药咨询 → 提示用户补充，流程到此终止； 否则写入本地存储，进入问答。
  3. 检索与证据提取 POST /api/evidence-pool
    • 疾病硬过滤 → 意图相关性判定（在本民族子段内查关键词，避免拿他族内容作答）
    • BM25 与向量余弦融合打分，叠加民族 / 疾病 / 意图权重
    • 表格键值检索：患病率类问题强制置顶数值表
    • 意图硬过滤 → 按来源去重
    • 聚焦片段截取（锚点按距离衰减）+ 计算原文偏移量
  4. 生成回答 POST /api/generate
    先判医疗安全边界 —— 命中则不检索、不喂证据，直接返回就医引导话术； 否则做越界清洗（他族 / 他病 / 无据数字），再交大模型按固定结构生成。
  5. 前端渲染
    依据文献（可展开、点击片段跳原文并定位高亮）、追问胶囊、收藏与分享按钮。

B · 文档摄取链路

  1. 上传 POST /api/kb/upload
    落盘 + 解析（docx 的表格转为 Markdown 保留结构），返回任务。
  2. 后台异步处理
    切片入库 → 大模型抽取结构化证据 → 生成内容摘要，三步都回调 AI 服务。
  3. 前端轮询进度
    书架卡片实时显示解析状态，完成即可检索。

C · 请求分流规则

改接口必看。开发环境下 Vite 按前缀分流，新增接口前缀必须同步修改 vite.config.ts，否则会被最后一条兜底规则转到 AI 服务而 404。 这条已经踩过一次：新增 /api/feedback 时漏了规则，界面上直接弹出一句 Not Found——那是 FastAPI 的 {"detail":"Not Found"}， 不是业务后端的报错。看到「Not Found」先查分流表，别去翻服务端日志。

D · 高级检索链路（主链路的短路版）

与 A 的区别只有一处：跳过 /api/understand。三个槽位由下拉给出， 直接调检索与生成，省掉一次大模型往返。

  1. 取词表 POST /api/ai/kb/vocab
    下拉里只列知识库真有资料的「民族 × 疾病」组合，以及该组合实际覆盖了哪些方面—— 免得用户选到一个必然查不到的组合。词表扫描的是切片文本（切片的民族/疾病字段是空的， 全靠子串匹配）。
  2. 检索 + 生成
    与 A 的第 3、4 步同一条链路，只是槽位由前端直接给定。
  3. 存档 POST /api/search-history
    把「答案 + 打包证据」存成快照（幂等键：用户 + 民族 + 疾病 + 方面）。存快照而不是重跑， 是因为重跑会因模型随机性给出与用户当时看到的不一样的答案——那不叫回放。
  4. 未命中则登记缺口
    证据池返回空时调 POST /api/gaps 记一条需求，用户可再点「反馈缺文献」 把自己的名字加上去。这条记录的去向见下面的 E。

E · 知识缺口闭环

这是本系统的第二个闭环（第一个是 A 的「提问 → 回答」）。它要回答的不是用户的问题， 而是知识库自己的缺口：哪些「民族 × 疾病 × 方面」有人要、但库里没有。

  1. 发现：两个来源各自留痕
    同一「民族 + 疾病 + 方面」全库只有一行（唯一键不含用户），但来源用两列标记分别记， 因为同一组合完全可能被两个入口都碰过：
    • 高级检索未命中 —— 自动登记。槽位是用户从下拉里选的，本身就是结构化的需求信号。
    • 智能对话未命中 —— 要用户点了【反馈此问题】才登记。那里的槽位是 NLU 猜的， 自动登记会把每一次猜测都变成一条需求，而猜测会错。
    两者可以同时为真，界面上两个来源徽标一起显示。
  2. 聚合：被问次数与反馈人数分开算
    ask_count 记「被要过几次」，feedback_count 记 有多少人想要（按用户去重，另存一张明细表）。 后者才是排序依据——若按点击次数累加，一个人连点 50 下就能把某条刷到榜首。
  3. 呈现：后台需求分析
    三个榜各回答一个问题：热门话题（大家在关心什么，按被问次数）、 未解决话题（还欠着什么，按反馈人数）、已解决历史。管理员在这里决定补什么。
  4. 补录：文献补录工作台
    从缺口点「去补充」进入，工作台预填关键词。管理员粘原文或传文件， 由 /api/ai/kb/extract-fields 抽结构化成表格行—— 知识库的形态是多文献汇编，不是单篇论文，所以补进来的东西必须逐条可溯源。 这份文档带着 gap_id 入库，且强制进待审核。
  5. 收口：审核通过且索引同步成功
    只打「通过」还不够——同步失败时文档根本没进检索索引，标成「已补充」会让缺口 凭空消失，比暴露更难发现。所以只有两个条件都满足才结掉缺口； 补录的那份文档后来被删掉时，缺口退回待补充。
两个缺口来源的判据不同，是刻意的。高级检索的三个槽位来自下拉，可信； 对话页的槽位来自 NLU，会错（例如「CKM」在服务端词表里就没有）。 与其让两边都自动登记、再想办法过滤噪声，不如让不可信的那一边必须由用户点头。

05关键设计决定

这些地方没有随大流选型，各有明确理由：

决定原因
不引 LangChain / 向量库知识库规模只有几十个切片，手写 BM25 + 余弦更好控、无重依赖
Java 管业务、Python 管 AI前端契约不变的前提下分层，便于将来把业务层整体迁到 Java
检索在整块切片上打分，展示用聚焦片段前者保召回，后者保可读性 —— 两者分开，用偏移量打通
医疗安全用独立布尔标记而非新增意图码5 码意图是检索主题匹配的依据与前后端契约，塞进第 6 个码会污染主题过滤
反幻觉用程序核对，不靠提示词把回答里每个百分比回查证据原文，比提示词可靠，且能自动回归
查询扩展默认关闭实测使检索通过率从 89.7% 降到 87.2%，两次运行一致 —— 召回本已饱和，扩展只带来打分扰动
两个缺口来源，只有可信的那个自动登记高级检索的槽位来自用户选的下拉，可直接采信；对话页的槽位来自 NLU，会错。不可信的来源必须由用户点一下才登记，否则每一次猜测都会变成一条需求
缺口来源用两列标记而不是一列枚举唯一键是「民族 + 疾病 + 方面」，同一组合可能既被检索记过、又被对话反馈过。一列枚举只能记一个，另一个入口的事实就丢了——榜单上会显示成「只有高级检索」，与用户刚做的事对不上
认不出疾病时存占位串而不是留空疾病列是 NOT NULL 且参与唯一键；留空的话 SQL 里 NULL 之间互不相等，同一组合每反馈一次就新建一行，「同一缺口全库一行」的前提就没了
「可选登录」与「排除拦截器」是两件事被排除的路径根本不解析 token，连已登录用户也会被当成匿名——对「匿名可用、登录则更好」的接口，那等于把登录用户的身份也丢了（发的帖显示不出昵称、列表回显不了「我点没点过赞」）。可选登录是「解析但不强制」
点赞 / 收藏 / 缺口反馈都按「人」去重一律 (目标, 用户) 唯一索引 + 明细表 COUNT。若是按点击累加，一个人连点就能把某条刷到榜首，排行榜失去意义
检索记录回放读存档快照，不重跑 RAG重跑会因模型随机性给出与用户当时看到的不同的答案，那不叫回放。代价是快照要单独设计形状（只留展示需要的字段，不带文档全文，否则单条记录会膨胀到几十 KB）

06评估体系

每次改动检索、提示词或问题理解后跑一遍 eval/run_eval.py，量化「改好了还是改坏了」， 不再靠手工挑几个问题试。

层检查内容依赖大模型
理解民族 / 疾病 / 意图 / 是否泛化 / 是否用药咨询间接
检索是否找到证据、意图缺失判定、证据里该有的数值在不在、是否被安全拦截否
回答该有的数值在不在、不该有的在不在、有没有编造文献外的数字是
最有价值的是「回答·无编造数字」。把回答里出现的每一个百分比都拿回证据原文核对， 对不上即判编造 —— 这是纯规则可自动化的检查，比让大模型当裁判更稳。

用例集分八类：精准检索、意图区分、泛化检索、负例·无证据、口语化、跨民族对比、泛民族、医疗安全。 期望值全部取自知识库里真实存在的内容，加用例前必须先确认库里有那个数，否则会得到假的失败。

07前端实现要点

前端不只是渲染层——问答本身是一个有状态的异步流程。下面几处是为了让它不出现 「答案串号、内容丢失、页面卡死」而做的设计，都不是照着常规写法来的。

并发：单飞锁

一次只允许一个问题在跑。锁加在 verify() 这个唯一入口上，而不是按钮上—— 推荐问题、追问胶囊、发送键、回车键四条路径都汇聚到这里，光禁用按钮挡不住键盘。

之所以必须加：analysisStore 是 Pinia 单例，却被当作「一次问答的临时缓冲区」用—— load() 把检索结果与生成结果写进 store，渲染时再从同一个 store 读出来。 同一来源的两条请求并发时会互相覆写，结果是 A 问题的卡片里渲染出 B 问题的答案。 所以这不只是「请求堆积变慢」，而是内容串号。

store 里现在有两条记录，不是一个槽位。原先只有一个槽位，于是「智能对话」与「高级检索」 这两个入口会互相覆盖：高级检索要打两次大模型、几十秒很正常，用户等不及切去对话页问一句， 两边谁后跑完谁占住工作台，另一方的分析被静默顶掉。 现在分成 records.dialogue / records.search 两条各存各的， 后台用「来源」开关选择看哪一条。但来源内部的并发仍然要靠单飞锁挡——拆开解决的只是跨入口的覆盖。

配套的三件事：

  • 解锁写在 finally——understand / load 抛错时也必须释放，否则页面永久卡死。
  • 锁不复用既有的按钮状态——那个状态会被输入事件改成「可发送」，锁会自己打开。
  • 生成期间禁止切换会话——在飞的请求完成后会把这一问一答写进切换后的会话，造成串号。选「禁止切换」而不是「取消请求」，是因为取消会让用户切回来时看到一个残缺的回答，反而更难解释。

乐观更新与「在途提问」

点下发送就立即清空输入框，并把提问气泡挂到对话流末尾，不等后端返回—— 用户马上看到「问题已经发出去了」，而不是盯着输入框里的原文怀疑到底发没发。 同时输入框禁用：问题一发出就不属于输入框了，改它也不会影响在跑的那一轮。

一个必要的补偿：问题被校验拒绝时（比如只说了民族、没说疾病）要把原文回填进输入框。 否则用户乐观清空后就丢了自己刚打的字，得整段重打——这是「乐观更新」在有校验环节的系统里必须配的一步。

一条线程：历史回放 + 本会话新增

打开旧会话（服务端消息）与在本会话里新问几轮，原本是两套渲染分支，靠「有没有历史」二选一。 代价是追问时必须先清空历史才能把显示权交给新回合——用户正读着的那几轮会当场消失。 现在两者合并成一条线程渲染：历史与新回合天然拼在一起，分享打包也因此拿到了完整对话 （此前只会分享出新问的那半截）。

「没答到点子上」的判据不只是「没检索到」

对话页在回答底部给一个【反馈此问题】入口，但它不能只在「一条证据都没检索到」时出现。 实际最常见、也最该反馈的是另一种：用户问「傣族CKM患病率」，系统没识别出 CKM （服务端词表里没有这个词），于是退化成「民族 + 意图」的泛化检索， 拿傣族糖尿病的数字作答——表面上「检索到了证据」，用户要的东西却没给到。

所以判据是「用户要的东西没给到」，三种情形满足其一：

信号含义
evidence_found = false一条证据都没检索到
generalized疾病没被识别出来，回答的是该民族的通用资料
intent_missing找到了背景资料，但没有一条对应所问的方面

排除医疗安全边界——用药 / 诊疗咨询是刻意不检索（见 A 的第 4 步），不是知识缺口， 把它引导成「我们会优先补充」就跑偏了。

「已反馈」为什么按槽位回显

理想的做法是把标记写进那一轮消息的 detail 里，精确到回合。做不到—— 没有「更新已存在消息」的接口（追加消息只能新增），而用户点反馈时那条消息早就落库了。

于是改成：进页面时拉一次「我反馈过的缺口」，按 民族|疾病|方面 比对。 代价是同一会话里对同一组合问两次、两轮都会显示已反馈；好处是刷新不丢， 还顺带覆盖了「换个会话问同一组合」。语义上也自洽——服务端本来就按 (缺口, 用户) 去重，同一组合再点一次是空操作，所以它一律显示「已反馈」才是诚实的。

配套的一个兜底：疾病槽位在 NLU 没认出来时，会退回前端自己的词表从原话里再认一次 （「CKM」前端有、服务端那 7 个疾病里没有）。不退这一步，缺口只能记成「未识别疾病」， 管理员得去读原话才知道用户要什么。

URL 交接

参数来源行为
?q=<问题>首页热门问题开一段新对话并自动提问；未登录时随 redirect 带到登录后再执行

08内容沉淀与三类书签

用户产出的东西要有地方落。这里刻意没有做一个统一的「收藏」—— 收藏的对象有三种，可见性各不相同，混在一张表里迟早会把私有的东西公开出去。

公开的那一侧：动态

类型来源幂等键
dialogue 多轮对话分享对话页「分享至动态」/ 个人中心(用户, 会话) —— 重复分享是更新标题与内容，不新增
qa 一问一答卡高级检索结果页 / 个人中心的检索记录qaKey = 民族|疾病|方面，全局唯一——同一组合在整个社区里只有一张卡，换个账号分享也是刷新

两者存成同一种载荷（{version:2, turns:[…]}），问答卡就是「只有一轮的对话」。 这样详情弹窗不用写两套渲染——它本来就按 turns 数组渲染，长度为 1 天然兼容。

私有的那一侧：三种书签各一张表

表收藏什么谁能看
user_favorite已发布的动态（含别人分享的）公开内容，收藏关系私有
user_conversation_favorite自己的对话私有书签，不公开发布
user_search_favorite一条高级检索记录私有书签
为什么收藏对话要单独一张表。早先没有它，收藏对话只能先转存成动态再收藏， 于是「点收藏」这个动作会把内容公开出去——私有书签与公开发布被绑成了一件事。 拆开之后，收藏就只是收藏。

个人中心的「我的收藏」把三类分组列出而不是合成一个列表：它们能做的事不同， 混在一起用户分不清哪条能点、哪条点了会跳去哪。

09用户反馈与身份策略

留言板是全站唯一不需要登录的业务页面：未登录也能浏览、也能发布。 它要回答的不是「知识库里缺哪个组合」（那是 04-E 的事），而是 用户自己说出来的、形状更宽的需求——可能指向知识库之外的东西， 甚至是抱怨。所以它不混进缺口榜，单独一块。

可选登录：解析但不强制

这是为了让「匿名可用、登录则更好」成立。项目的鉴权默认是对所有 /api/** 一律要求登录，而「放行某些路径」的现成手段是 excludePathPatterns——但被排除的路径根本不进拦截器， token 不会被人解析，连已登录用户也会被当成匿名。

后果很具体：已登录用户发的帖会显示成「匿名用户」， 列表也回显不了「我点没点过赞」（没有身份就无从判断）。 所以另加了一组「可选登录」路径（配置项 app.auth.optional-paths）： 命中这些路径时，token 有效就照常注入 userId，没有或已失效就放行当匿名，不抛 401。

失效 token 在可选路径上按匿名处理而不是 401：公开页面上因为 token 过期就被弹回登录页 很恼人，而这条路径本来就有匿名能力，降级是合理的。

哪些动作要登录，哪些不要

动作要登录吗原因
浏览留言板 / 发布反馈不要公开页面，发布者记为空则显示「匿名用户」
点赞要「同一用户只能点一次」没有身份就无从去重，匿名点赞无法保证不被连点刷榜
改状态 / 一键转缺口 / 看榜单要，且需管理员运营动作。管理员 = 配置文件里的官方账号白名单，用户表里没有角色字段
「可选登录」的边界要精确到具体路径。配置里写的是 /api/feedback 本身， 而不是 /api/feedback/** —— 后者会把点赞、改状态、转缺口这些深一层的路径 一并放行，那些都是必须有身份的操作。同一条经验在知识库那边也有： 放行范围写成 /** 会把上传、删除一起放出去。

与知识缺口的关系

留言板里的「请求补充某民族某疾病」可以由管理员一键转为知识缺口， 于是它也成了缺口的一个来源。它既不是检索未命中、也不是对话里点出来的， 所以在缺口表上两个来源标记都是 0——界面上给它一个中性的徽标， 而不是硬塞进已有的两类里。

转缺口时需要的三个槽位由前端从反馈原文里识别后传上来 （复用前端那份民族 / 疾病词表），服务端不重新实现识别： Java 侧没有这份词表，再写一份就是第 N 份拷贝——这个项目已经因为 「同一份词表多处维护、互不一致」吃过亏（服务端 NLU 的 7 个疾病里就没有「CKM」，而前端有）。
