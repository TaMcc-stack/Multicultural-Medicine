隧道部署手册

三个跑在自己电脑上的服务——前端 5173、后端 8080、AI 8000——用一个免费隧道发布到公网， 让别人用手机就能打开。下面是完整六步，以及我们实际踩过的八个坑。

cloudflared quick tunnel 零成本 · 免账号 网址每次重启都会变

01整体架构

核心思路：只把 5173 这一个端口暴露出去。前端 Vite 自己当网关， 按 /api 前缀把请求分给后端和 AI。这样隧道只需要一条， 后端和 AI 完全不碰公网。

浏览器 评委 / 同学的手机或电脑
https://xxxx.trycloudflare.com
Cloudflare 隧道 cloudflared.exe · 唯一的公网入口
localhost:5173
前端 :5173 Vite · 发页面 + 当网关
按 /api 前缀分流
后端 :8080 Spring Boot
AI :8000 Python FastAPI

分流规则写在 frontend/vite.config.ts 的 proxy 里。规则按数组顺序匹配， 所以具体前缀必须排在 /api 兜底之前：

请求前缀 → 实际服务。顺序即优先级，写反了就会走错服务。
请求前缀转发到管什么
/api/auth:8080登录、注册、个人资料
/api/conversations:8080会话管理
/api/qa:8080问答编排
/api/kb:8080知识库业务
/api/dynamics:8080动态
/api/favorites:8080收藏
/api/search-history:8080高级检索历史
/api/gaps:8080知识缺口 / 需求分析
/api/feedback:8080反馈留言板
/api/health:8080后端健康检查
/api:8000兜底：检索、生成、理解等 AI 接口

为什么不让隧道暴露三个端口？免费版 quick tunnel 一次只给一个随机域名。想暴露三个，就得开三条隧道、拿三个网址——前端还得知道另外两个在哪，跨域问题也随之而来。让 Vite 当网关，一条隧道、一个网址、同源，全都省了。

02部署六步

前三步是本地准备，第四步改配置，第五步开隧道，第六步验证。全程不需要买服务器。

懒人版：双击 Start\start-demo.bat 就行。它把下面六步全做完了——起服务、打包、起前端、开隧道、抓网址、自动验证——还会把网址复制到剪贴板、存档到 Start\当前演示网址.txt。

下面六步是对应的人工流程，看懂它才能在有一步出错时知道该查哪里。

01

起三个服务

三个服务各开一个窗口，顺序无所谓，但要都起来：

ai-service\restart-ai.bat        # → :8000
backend\restart-backend.bat      # → :8080
frontend\restart-frontend.bat    # → :5173

嫌麻烦就用一键脚本 Start\start-all.bat，它会开三个窗口分别拉起。

AI 服务必须用 restart-ai.bat 里写死的解释器（Python 3.12）。项目里的 .venv 是坏的，直接调会报「did not find executable」。

02

打包前端 —— 这一步决定快慢

cd frontend
npm run build-only      # 只打包；npm run build 会多跑一遍 vue-tsc 类型检查

产物落在 frontend/dist/。

为什么必须打包？开发模式（npm run dev）下，浏览器要分几百次去要一个个小模块文件。走隧道时每个请求都要跑一趟「你 → 美国节点 → 回来」，几百次往返叠加起来，第一次打开能等几十秒。打包之后几百个请求合并成三个文件（HTML + JS + CSS），从几十秒降到几秒。

03

改 vite.config.ts 的三处

这是唯一需要动代码的地方，三处缺一不可：

// ① 白名单：Vite 默认只放行 localhost，隧道域名会被它 403 拦掉
const allowedHosts = ['.trycloudflare.com']

// ② 代理：每条规则都摘掉 Origin 头（原因见坑 2）
function apiProxy(target) {
  return {
    target,
    changeOrigin: true,
    configure(proxy) {
      proxy.on('proxyReq', (req) => req.removeHeader('origin'))
    },
  }
}

export default defineConfig({
  server:  { host: true, port: 5173, allowedHosts, proxy },
  // ③ preview 块：让打包产物也能被访问、也能代理
  preview: { host: true, port: 5173, appType: 'spa', allowedHosts, proxy },
})

preview 块要和 server 段完全一致（端口、白名单、代理）。只配了 server 的话，npm run preview 起来后代理和白名单都是空的，页面照样打不开。

04

用 preview 起前端

npm run preview      # 还是 5173，但发的是打包产物

要先把原来的 dev 进程关掉，否则端口冲突。

隧道指向的是端口而不是某个进程，所以换进程不会改变网址——这也是为什么可以先开隧道、再从容地重起前端。

05

起隧道

先下载 cloudflared.exe（单文件、免安装，放进项目根目录），然后：

cloudflared.exe tunnel --url http://localhost:5173

输出里会有一行框起来的网址，抄下来就是公网入口：

INF |  https://xxxx-xxxx-xxxx-xxxx.trycloudflare.com  |

这个网址每次重启都会变。免费的 quick tunnel 不给固定域名，这是它的固有特性，不是配置问题。所以演示当天不要中途重启隧道。

06

验证四件事

把网址填进去，四条全过才算通：

$base = "https://你的隧道网址"

# ① 首页
Invoke-WebRequest "$base/" -UseBasicParsing | Select-Object StatusCode

# ② 后端
Invoke-WebRequest "$base/api/health" -UseBasicParsing | Select-Object -Expand Content

# ③ AI
Invoke-WebRequest "$base/api/ai/health" -UseBasicParsing | Select-Object -Expand Content

# ④ 登录 —— 必须带 Origin 头，否则测不出 CORS 问题（见坑 2）
$bytes = [System.Text.Encoding]::UTF8.GetBytes('{"username":"demo","password":"123456"}')
Invoke-WebRequest "$base/api/auth/login" -Method POST `
  -ContentType "application/json; charset=utf-8" -Body $bytes `
  -Headers @{ Origin = $base } -UseBasicParsing | Select-Object StatusCode

测 POST 接口务必带 Origin 头。浏览器对 POST 一定会发这个头，而命令行默认不发——不带 Origin 测出来是 200，浏览器里却是 403。我们就是在这里绕了一大圈。

另外，中文请求体要用 [System.Text.Encoding]::UTF8.GetBytes() 转成字节再发。PowerShell 5.1 直接传字符串会按 Latin-1 编码，中文变乱码，接口会返回一堆 null，看着像服务坏了。

03八个坑

下面每一条都实际发生过。共同点是报错信息都不说人话—— 所以记「症状」比记「原因」更有用。

坑 1

Vite 拦 Host，整页 403

症状
打开网址是一片白，页面写着 Blocked request. This host is not allowed.
根因
Vite 有个安全机制：只放行 localhost 的 Host 头。隧道的 Host 是 xxxx.trycloudflare.com，被它当成攻击挡掉了。
修法
server.allowedHosts: ['.trycloudflare.com']。前面那个点表示匹配任意子域名，这样换网址也不用改。
坑 2

CORS 拦 Origin —— 最阴的一个

症状
页面一切正常，首页能开、健康检查也通，但一点登录就弹「网络异常，请稍后重试」。发消息、注册同样挂。
根因
浏览器对非 GET 请求一定会带 Origin 头，即使是同源请求（这是浏览器规范，很多人不知道）。后端的跨域白名单只写了 http://localhost:*，隧道域名不在里面，Spring 直接回 403 Invalid CORS request。响应体是纯文本，前端解析不出内容，只好显示兜底文案——所以提示文不对题。
修法
在 Vite 代理转发时把 Origin 摘掉。经代理转发后，后端看到的本来就是同源请求，摘掉完全合理；而且隧道网址每次都会变，摘头不依赖具体域名，比往白名单加域名一劳永逸。

「GET 全好、POST 全挂」就是这条的特征，不是「没连上后端」。另外，Python/FastAPI 那边没有这个问题——它的跨域中间件遇到不认识的 Origin 只是不加响应头，不会拒绝请求。所以这个坑只在 Spring 那条链路上。

坑 3

开发模式慢到像卡死

症状
第一次打开要等几十秒，转圈转到以为挂了。
根因
npm run dev 不给打包产物，浏览器要分几百次去要一个个模块。每个请求都要走一趟「中国 → 美国节点 → 回来」，几百次叠加。
修法
npm run build-only 打包，然后用 npm run preview 起服务。
坑 4

代理前缀顺序写反

症状
界面弹一个 Not Found。后端日志里什么都没有。
根因
新加的接口前缀没排在 /api 兜底之前，请求被转发给了 Python，拿到 FastAPI 的 {"detail":"Not Found"}。
修法
把具体前缀写在 /api 兜底之前。代理规则是按顺序匹配的，顺序就是优先级。
坑 5

HTTP/2 协议注册不上

症状
隧道起不来，日志报 Register tunnel error ... context deadline exceeded，进程退出。
根因
换用 --protocol http2 后，这条网络下注册握手超时。前置检查全 PASS，但实际连不上。
修法
用默认的 QUIC 就好（--protocol quic 或干脆不加参数）。QUIC 虽然偶尔报 wsasendto 缓冲区不足，但会自动重连，不影响使用。
坑 6

换网络 = 隧道当场断

症状
用着好好的，忽然报网络错误。
根因
电脑换了网络（比如从 WiFi 切到手机热点），切换的一瞬间所有连接被掐断，隧道跟着断。
修法
刷新页面即可恢复。演示当天千万别切网络——别从 WiFi 切热点，也别让笔记本在 WiFi 之间漫游。
坑 7

新建的隧道没有 DNS 记录（被限流）

症状
脚本显示隧道建好了、也拿到了网址，但四项验证全挂，域名根本解析不出来。隧道日志里却明明白白写着 Registered tunnel connection。
根因
Cloudflare 对免费 quick tunnel 有创建频率限制。短时间内反复重建隧道（调试时最容易犯——每次改点东西就重启一遍），新域名就拿不到 DNS 记录。用 DoH 查会看到记录可能已存在，但本地解析不到。
修法
等 30～60 分钟（或重启电脑），再建一条。期间不要反复重启隧道——每重启一次都会加重限流。
本机服务不受影响，可以先在浏览器里用 http://localhost:5173 演示。

一条经验：调试阶段尽量复用同一条隧道，别每次改动都重启它。隧道的 DNS 一旦生效就不会再变，改前端代码只要重启 5173 上的进程就行（隧道指向的是端口，不是进程）。

坑 8

本机 DNS 不给 IPv4，网址打不开

症状
隧道建好了、日志里 Registered tunnel connection 也在，但浏览器打开网址就是转圈然后失败。只有你这台电脑这样，别人的手机正常。
根因
这条网络的 DNS 服务器对 *.trycloudflare.com 的 IPv4（A 记录）查询直接回 NXDOMAIN，只肯给 IPv6（AAAA）；而这条网络的 IPv6 又出不了网。两头堵死。实测：nslookup -type=A 回「Non-existent domain」，但公共 DNS 全都查得到。
修法
把网卡的 DNS 换成公共 DNS（管理员 PowerShell）：
Set-DnsClientServerAddress -InterfaceAlias WLAN -ServerAddresses 223.5.5.5, 119.29.29.29
Clear-DnsClientCache
想改回去：Set-DnsClientServerAddress -InterfaceAlias WLAN -ResetServerAddresses

别用「禁用 IPv6」来修：A 记录本来就是 NXDOMAIN，禁了 IPv6 就一个地址都拿不到，反而更糟。

start-demo.bat 每次会自检这一点，并直接打出上面那条命令——看到提示照抄即可。它还会用 --resolve 绕过坏 DNS 去验证隧道，所以「验证通过但浏览器打不开」时，问题一定在这台机器的解析上。

还有一条不算坑但要知道：免费隧道没有可用性保证，Cloudflare 官方明确说了不承诺 uptime。演示当天它可能自己抖一下——刷新页面能救回来。真要稳定得上付费的固定域名隧道，但演示场景没必要。

04演讲当天

开始讲之前照着勾一遍。勾选状态会存在你自己的浏览器里，换台设备要重新勾。

现场如果卡住了：先 Ctrl+F5 刷新。八成是网络抖了一下，刷新就好。别急着重启服务——重启隧道意味着网址会变，正在看的人全断。

05故障速查

从「你看到什么」倒查，比从原因正查快得多。

症状 → 大概率原因 → 第一个动作
你看到的大概率是先做什么
整页 403 Blocked request Vite 拦 Host 检查 allowedHosts 有没有配；配了还不行就看看是不是配在了 server 而 preview 没配
弹窗 网络异常，请稍后重试 Spring 拦 Origin（坑 2），或隧道刚断过 先刷新重试；还挂就查代理有没有摘 Origin
弹窗 Not Found 代理前缀顺序（坑 4） 把新前缀挪到 /api 兜底之前
整页 502 / 530 隧道断了，或前端没起 看 5173 在不在、cloudflared 进程还在不在
域名 解析不出来 两种可能：被限流（坑 7），或本机 DNS 不给 IPv4（坑 8） 看 start-demo.bat 的提示——它已经帮你区分了：说「公网记录是有的」就是坑 8，改 DNS 即可
第一次 加载几十秒 跑的还是 dev 模式（坑 3） 确认用的是 npm run preview，不是 npm run dev
用着用着 忽然全挂 换网络了（坑 6） 刷新；确认电脑网络没变过
每个操作 都等 2～5 秒 正常现象 流量绕道海外节点，属预期。别当成卡死
