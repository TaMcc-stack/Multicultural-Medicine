# RAG 评估体系

每次改动**检索 / 提示词 / 问题理解**后跑一遍，量化「改好了还是改坏了」，避免靠手工挑几个问题试。

## 三层检查

| 层 | 检查什么 | 是否依赖大模型 |
| --- | --- | --- |
| 理解 | 民族 / 疾病 / 意图 / 是否泛化 | 间接（理解层用了 LLM） |
| 检索 | 是否找到证据、意图缺失标记、证据里该有的数值在不在 | 否 |
| 回答 | 回答里该有的数值在不在、不该有的在不在、**有没有编造文献外的数字** | 是 |

「回答层·无编造数字」是最有价值的一条：把回答里出现的每个百分比都拿回证据原文里核对，对不上就判编造。

## 用例分类（`eval/cases.json`）

| 分类 | 覆盖 |
| --- | --- |
| 精准检索 | 民族 + 疾病 + 意图 三要素齐全 |
| 意图区分 | 同一民族疾病、不同意图应返回不同证据 |
| 泛化检索 | 只识别出民族 + 意图（疾病缺失），应降级检索而非拒绝 |
| 负例·无证据 | 知识库确实没有的内容，应如实返回「无证据」且**不得拿其它数据作答** |
| 口语化 | 长辈口吻 / 生活场景的提问 |
| 跨民族对比 | 问句涉及多个民族 |

期望值全部取自《数据资料》《专家共识》里**真实存在**的内容。加用例时请先确认知识库里确实有这个数，否则会得到假的失败。

## 结果文件

写入 `eval/results/eval-<时间戳>.json`，含每条用例的逐项断言、证据条数、耗时、幻觉数字列表。

做基线时用 `--out eval/results/baseline.json`，之后 `--compare` 就能看退化/改善。

## 已知局限

- **答案层有随机性**：同一问题两次生成的措辞可能不同，`answer_contains` 偶发波动属正常。判断趋势看整体通过率，别看单条。
- **负例的 `answer_not_contains`** 是在防「拿患病率数据硬答饮食问题」这类越界，属于强约束——它失败了通常意味着提示词约束被绕过，值得查。
- 用例数还少（20 条），覆盖面以现有知识库（2 份资料）为限。
